# 主线与支线：协调者手册

长任务一直在一个对话里做，对话会被一次次压缩，细节就丢了。这个 skill 的做法：

- **协调者**（调用本 skill 的会话）：理解需求、侦察、拆线、写任务书、开会话、收汇报、合并、验证、跟用户沟通。协调者自己不写大段实现，上下文留给全局。合并冲突、一两行的小修可以自己改。
- **线**：每条线一个侧边栏会话，在自己的 worktree 里照任务书干活，做完把汇报发回协调者。用户可以直接进那个会话跟它聊。
- **账本**：`~/.claude/mods-data/task-lines/boards/<账本 id>/`，所有细节都落在这里。对话会被压缩，账本不会。task-lines 插件会在压缩后把账本自动放回上下文：协调者拿回 board.md 和 log.md 的最新部分，线拿回自己的任务书和进度。

下文的 `scripts/` 指本 skill 目录下的 scripts 文件夹（加载本 skill 时显示的 Base directory）。

## 开工

1. **建账本**：调用 `task_board`，`title` 填任务的短标题。再用 `mcp__ccd_session_mgmt__get_session`（session_id 填 `self`）拿到本会话的桌面端会话 id（`local_` 开头），填进 board.md。线要用这个 id 给你发汇报。
2. **记原话**：把用户的需求逐字贴进 board.md 的「用户原话」。不要改写，也不要只写摘要。
3. **侦察**：读到能把任务书写清楚为止，包括相关代码、文档和项目的 CLAUDE.md。要弄清现状、相关文件、项目约定和验证命令。结论写进「约束与已定的决定」。
4. **拆线**：按下面「怎么拆」的规则拆，写进「线」表。
5. **拍基线**：运行 `scripts/snapshot.sh <主目录> refs/task-lines/<账本 id>/base-1`，把输出的提交 id 写进「当前基线」。快照包含主目录里还没提交的改动和未跟踪的文件，但不动暂存区、HEAD 和分支。
6. **写任务书**：给每条现在就能开工的线写 `lines/<线 id>/brief.md`，按下面的模板写。
7. **开会话**：每条线调用一次 `mcp__ccd_session__spawn_task`：
   - `title`：`[L1] 动词开头的短标题`，60 字以内。`[线 id]` 前缀以后用来找回这个会话。
   - `tldr`：一两句人话，说这条线做什么。
   - `prompt`：任务书全文。prompt 必须能独立看懂，不能只写「去读账本」。

   每条线会出现一张卡片，用户点一下才会开出会话。新会话自带一个独立的 worktree。
8. **告诉用户**：拆成了哪几条线、各做什么、哪几条现在就能开、哪几条要等前面的合并后才开，并请用户点卡片。拆完直接开工，不用等用户批准计划；用户随时可以叫停或改。
9. **记流水**：用 `task_note` 记一笔。

## 怎么拆

- **主线**是任务的主干。很长的主线按阶段切成 L1、L2……，每个阶段开一个新会话，从最新的基线开工。每个会话只装一个阶段的上下文，这是防丢细节的关键。
  - 阶段之间串行：上一阶段合并、验证完，再拍新基线、写下一阶段的任务书，任务书里写上上一阶段的交接。
- **支线**是和主线相对独立的活，比如另一个模块、工具脚本、补测试、调研。支线可以和主线同时跑，id 用 S1、S2……
- **一条线的大小**：一个会话能从头做到尾，不至于被压缩好几次。拿不准就切小一点。
- **同时跑的线，尽量别改同一批文件**：worktree 只隔开了各自的运行，改到同一处，合并时还是要解冲突。
  - 共用的接口（函数签名、数据格式、文件路径）开工前就定好，原文写进每条相关的任务书。
- **同时开几条**：一般 2 到 3 条。每条线都可能找用户批权限、问问题，开多了用户顾不过来。
- **不值得拆的不拆**：一个会话能顺利做完的任务，直接做，不用开账本。

## 任务书模板

尖括号里的内容由协调者填。不适用的节写「无」，不要删掉。

```markdown
# [<线 id>] <标题>

你是任务账本 <账本 id> 里的一条线，协调者是另一个会话。照下面做，做完把汇报发回协调者。

## 开工先做
1. 调用 task_line_attach，board 填 "<账本 id>"，line 填 "<线 id>"。这个工具来自 task-lines 插件；没有这个工具就跳过这一步，并在汇报里说明。
2. 确认你在自己的 worktree 里：`git rev-parse --show-toplevel` 的输出不能是 <主目录>。如果是，停下来，告诉用户。
3. 对齐基线：先确认 `git status --porcelain` 的输出是空的，再运行 `git reset --hard <基线提交>`。基线里有主目录里还没提交的改动，不对齐的话，你的改动合不回去。
4. 准备环境：<例如 pnpm install。worktree 里没有 node_modules，Rust 的 target 目录也是空的，第一次编译会比较慢>

## 背景与目标
<用户原话里和这条线有关的部分，逐字照抄；这条线做完应该是什么样子；为什么要做>

## 已知事实
<侦察的结论：相关文件和行号、现状、项目约定、可以照抄的现成写法、已经定下的决定>

## 范围
- 可以改：<文件或目录>
- 不要碰：<文件或目录>
- 同时在跑的其他线：<线 id：改哪些文件>
- 主目录 <路径> 一律不碰，只在自己的 worktree 里改。

## 接口约定
<和其他线共用的签名、格式，原文照抄>

## 验证
<具体命令：测试、类型检查、构建、实际跑一遍。涉及界面的要截图，亲眼看>

## 纪律
- 可以在自己的分支上 commit 存档，不要 push，不要动别的分支。
- 遵守项目 CLAUDE.md 里的约定。
- 关键的决定、发现和进度，用 task_note 记下来。对话被压缩以后，你要靠它接着做。
- 用户在这个会话里直接提的新要求，照做，并在汇报里把原话转告协调者。
- 需要协调者或用户拍板的事，或者超出范围的事：先用 task_note 记下，再发消息问协调者，不要自己扩大范围。

## 做完
用 SendMessage 发给协调者，to 填 "<协调者的桌面端会话 id>"。没有 SendMessage 就用 mcp__ccd_session_mgmt__send_message，session_id 填同一个 id。
第一行写「[<线 id>] 完成：<一句话>」，后面依次写：
- worktree 路径（`git rev-parse --show-toplevel` 的输出）和分支名
- 改了什么（按文件列）、为什么这样改、自己做了哪些取舍
- 验证：跑了哪些命令、真实的结果。红了就说红了。
- 遗留问题，以及需要协调者或用户决定的事
- 用户在这个会话里提的新要求（原话）
同样的汇报也用 task_note 记一份。发完就停下，等协调者回复，他可能会让你返工。
```

## 线在跑的时候

- **不要轮询**。线做完会发消息过来，显示为来自那个会话的消息。
- **查进度**：用户问进度时，用 `mcp__ccd_session_mgmt__list_sessions` 按标题前缀 `[线 id]` 找到会话，再用 `mcp__ccd_session_mgmt__list_events` 看它最近在做什么。找到的会话 id 记进线表。
- **线来问问题**：能定的直接回复那个会话，并记进账本。要用户定的，转去问用户。
- **用户在主对话里提了新要求**：先逐字追加到 board.md 的「用户原话」，注明时间。再判断影响哪条线：发消息告诉那条线，或者留到下一阶段再处理。
- **线卡住或跑偏**：发消息纠正。

## 收线与合并（每条线都要做）

1. **预演**：先读汇报，再运行
   `scripts/merge-line.sh --check <主目录> <这条线的基线> <线的 worktree 路径>`。
   它会列出将要更新、三方合并、新增、删除的文件，以及哪些会冲突。最后一行给出查看这条线完整 diff 的命令。
2. **审查**：
   - 有没有改到范围以外的文件；
   - 逻辑对不对，像不像项目里原有的代码；
   - 有没有多余的东西；
   - 注释和文字是否符合项目约定。

   不合格就发消息让线返工，写清楚哪里不对、要改成什么样，返工完从第 1 步再来一遍。
3. **合并**：运行 `scripts/merge-line.sh <主目录> <基线> <线的 worktree 路径>`。它只改主目录工作区里的文件，不动暂存区、HEAD 和分支。
   - 有冲突时，文件里会留下冲突标记（`<<<<<<< 当前` 到 `>>>>>>> 线`）。冲突不多就自己解；多或者看不明白，先停下来告诉用户，再商量怎么办。
   - 脚本拒绝合并（退出码 2，提示「不是从基线开始的」）：说明线开工时没有对齐基线。问那条线是怎么回事，不要硬合。
4. **验证**：在主目录跑全量检查，包括项目的测试、类型检查和构建。脚本只做文件层面的合并，不跑检查就不算合完。
5. **记账本**：线表里的状态改成「已合并」。在「合并记录」里写：时间、线、基线、快照 id、合并结果（冲突怎么解的）、验证结果。
6. **告诉用户**这条线合进来了什么。提不提交由用户决定。用户没要求时不 commit；要提交就按项目的提交约定。
7. **线的会话**：合并完、用户也不用再回去看时，问用户要不要归档（`mcp__ccd_session_mgmt__archive_session`）。不要自己删 worktree。

## 下一阶段

主线的下一阶段，或者依赖已合并线的支线，按这个顺序开：

1. 拍新基线：`scripts/snapshot.sh <主目录> refs/task-lines/<账本 id>/base-<n>`。
2. 更新 board.md 的「当前基线」。
3. 写任务书，写明新基线，以及上一阶段的交接：做了什么、留下了什么、要注意什么。
4. 开新卡片。

还在跑的老线继续用它们自己的基线。合并脚本按每条线各自的基线做三方合并，互不影响。

## 压缩之后

task-lines 插件会把 board.md 和 log.md 最近的部分放回上下文。继续之前：

1. 对照账本的线表，用 `list_sessions` 找到各条线的会话（标题前缀 `[线 id]`），用 `list_events` 看它们现在的状态。
2. 摘要里有、账本里还没有的东西（新的决定、用户新提的要求），先补进账本。
3. 然后接着做。

摘要和账本对不上时，以账本和实际状态为准，实际状态看会话记录和 git。

## 账本怎么记

- **board.md 是总账**：用户原话、目标、约束、已定的决定、线表、合并记录、待用户决定的事。直接编辑这个文件，让它始终反映现在的真实状态。
- **log.md 是流水**：用 `task_note` 追加，记什么时候定了什么、收到什么汇报、合并结果如何。
- **每个里程碑后都要更新**：拆完线、开卡片、收到汇报、合并完、用户改需求。账本落后于对话的话，一压缩细节就丢了。
- 账本里不写密钥、密码和令牌。

## 换一个会话当协调者

原来的协调者会话太长了，可以新开一个会话接手：

1. 调用 `task_board`，`board` 填账本 id。
2. 按「压缩之后」一节核对一遍。
3. 线发汇报用的是原协调者的会话 id。把 board.md 里的会话 id 改成新会话的，并给每条还在跑的线发一条消息，告诉它以后把汇报发到哪里。

## 要留意的

- 线只能开在用户自己在桌面端打开过的项目里。Claude 在 scratchpad 或其他会话可写目录里新建的仓库，桌面端出于安全考虑不给建 worktree，用户点卡片只会看到「Couldn't start the suggested task」。spawn_task 的 `cwd` 不填（默认当前项目），或者填用户打开过的项目路径。
- 卡片开不出来时，Claude 这边收不到任何通知，要靠用户告诉你。原因写在桌面端日志 `~/Library/Logs/Claude/main.log` 里，搜 `createWorktree` 或 `Worktree creation failed`。
- 线会话的 worktree 里没有被忽略的目录，比如 node_modules 和 Rust 的 target。任务书的「准备环境」要写清楚怎么补。
- 基线快照保存在 `refs/task-lines/<账本 id>/` 下，不出现在分支列表里。整个任务结束后可以用 `git for-each-ref refs/task-lines/<账本 id>` 列出来、用 `git update-ref -d` 删掉，删之前问用户。
- 两个会话的权限模式不同时，它们之间的消息要先等用户批准。开线时提醒用户留意。
- merge-line.sh 处理文本文件和普通文件。符号链接，以及两边都改了的二进制文件，会列为「需手动处理」。

## 收尾

所有线都合并、全量验证也通过以后：

1. board.md 标为「已完成」。
2. 向用户汇报：每条线做了什么、合并结果、验证结果、遗留问题、待用户决定的事。
3. 问用户要不要归档各条线的会话、要不要清理基线快照。
